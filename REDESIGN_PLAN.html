사용자는 두 가지 방식만 알면 됩니다. LLM이 화면을 보고 직접 작업하거나, 하나의 프로세스 편집창에서 녹화·요소 선택으로 작업을 만듭니다. 두 방식은 같은 인식·입력·검증 엔진을 사용합니다.

이 문서는 구현을 위한 설계안입니다. 이번 검토에서는 첨부 대화와 소스 코드를 분석했으며, MuMu의 새 실행 시험이나 제품 코드 변경·배포를 수행하지 않았습니다.

실패 원인두 가지 사용 흐름통합 편집창대화로 수정엔진 구조속도구현 순서출시 기준개발 계약

1. 이번 MuMu 사례에서 실제로 확인된 문제

실행 버튼을 인식하지 못한 상태에서 목록의 행 자체를 클릭했습니다. 모델은 화면 이미지를 받지 못했고, UIA에도 행 안의 실행 버튼은 없었습니다. 실제 시작 버튼에 정확한 전경 클릭을 보내는 경로는 시험하지 못했습니다. 따라서 이번 기록만으로 Driver의 입력 성능이 낮다고 확정할 수는 없습니다.

확인한 내용판정설계에 반영할 점
앱 실행·창 발견·UIA 요소 41개 읽기첨부 대화에서 확인실행 자체보다 목표 버튼 인식 이후 경로가 핵심입니다.

녹화·저장·재생이 이 MuMu 환경에서 성공했는지기록 없음첨부는 편집창을 연 시점에서 끝납니다. 녹화 실패 원인까지 이 기록으로 단정하지 않습니다.
이전 시험 앱의 녹화·재생 통과는 MuMu와 사내 앱의 성공을 보장하지 않습니다. 다음 출시는 실제 대상 앱에서의 성공률과 소요 시간을 별도로 공개해야 합니다.
소스에서 확인한 구조적인 문제 7가지
  1. 화면 이미지 전달이 기본 차단됩니다. image_delivery.py:116의 text 기본값과 최종 응답 필터 때문에 이미지 없는 LLM이 그래픽 버튼을 이해할 수 없습니다. 텍스트 모델 호환 정책은 필요하지만 사용 가능 범위를 명확히 구분해야 합니다.
  2. 관찰이 작업 목표를 고려하지 않습니다. inspection.py:232–241은 이름 있는 조작 요소가 하나라도 있으면 UIA가 충분하다고 판단할 수 있습니다. 주변 메뉴가 읽혀도 정작 실행 버튼이 없을 수 있습니다.
  3. UIA와 이미지 조작 경로가 분리돼 있습니다. operations.py:304–315, vendor/guard.py:572–599의 세션 모드 제약 때문에 주력 동작 API 안에서 자연스럽게 혼합하기 어렵습니다.
  4. 동일 아이콘을 행 안에서 찾는 계약이 없습니다. image_targets.py:73–85에는 이미지·클릭 위치는 있지만 목록 영역·행의 이름·행 내부 상대 관계가 없습니다.
  5. 이미지 재생이 사람 확인의 연속이 됩니다. workflows.py:59,79–110은 자동 완료 조건 없는 이미지 입력 뒤 로컬 확인 단계를 요구합니다. 이미지·창 변화 기반 자동 완료 조건이 부족합니다.
  6. LLM에 기능이 평면적으로 너무 많이 노출됩니다. server.py:610에서 관리 도구 32개와 Driver 저수준 도구를 합칩니다. 모드별 차이가 있지만 전체 종류는 최대 48개입니다.
  7. 안전한 부분 수정 API가 없습니다. TaskStore.save는 전체 교체 방식이고 process_editor.py:103의 조회 결과는 이미지 원본을 숨깁니다. 조회→일부 수정→전체 재저장은 이미지 작업 수정의 올바른 계약이 아닙니다.

2. 사용자가 고르는 것은 두 가지뿐입니다

A. 말로 시켜서 실행

“MuMu 목록의 맨 위 두 개를 실행해줘.”
  1. 프로그램과 현재 창을 찾습니다.
  2. 실제 화면과 필요한 요소 정보를 함께 읽습니다.
  3. 첫 두 행과 각 행의 실행 버튼을 구분합니다.
  4. 한 번씩 누르고 각 인스턴스의 실행 상태를 확인합니다.
  5. 완료 결과 또는 딱 막힌 단계만 알려줍니다.

사용자는 UIA/이미지/전경/배경이나 PID를 선택하지 않습니다.

B. 한 번 보여주고 반복

“내가 하는 작업을 녹화해서 반복 작업으로 만들어줘.”
  1. computer_process_editor 하나를 엽니다.
  2. 녹화 시작 후 평소처럼 작업합니다.
  3. 녹화 마침을 누르면 단계·입력값·완료 조건이 정리됩니다.
  4. 잘못된 단계만 고치고 시험 실행합니다.
  5. 이름을 붙여 저장한 뒤 말로 다시 실행합니다.

녹화하지 않고 단계 추가 → 화면에서 선택으로 만드는 것도 같은 편집창 안에서 합니다.

LLM 조건은 명확하게 안내합니다. 처음 보는 그림·아이콘까지 알아서 찾으려면 화면을 이해하는 사내 모델 또는 승인된 사내 시각 인식 서비스가 필요합니다. 텍스트 전용 LLM에서도 UIA·화면 글자·저장된 이미지 작업은 사용할 수 있지만, 처음 보는 무문자 아이콘의 의미까지 자동 판단한다고 약속하지 않습니다.

설치할 때 연결 환경을 한 번 확인하고 “화면 이해 가능 / 요소·글자 기반 / 기록 작업 실행 가능”으로 표시합니다. 일반 사용자에게 이미지 챌린지나 JSON 편집을 매번 요구하지 않습니다. MCP 연결만으로 모델의 이미지 이해 능력을 추정하지 않습니다. 기존 이미지 차단 정책을 자동 해제하지 않고 승인된 연결 프로필을 사용합니다.

3. 프로세스 편집창 하나로 통합

별도 요소 학습, 이미지 학습, F8 선택, 녹화 도구를 오가게 하지 않습니다. 사용자가 직접 대상을 가리키는 진입점은 computer_process_editor 하나입니다. 내부 도우미가 필요하더라도 같은 편집 작업 안에서 열리고 결과가 해당 단계로 돌아옵니다.

화면에서 선택

사용자가 가리킨 버튼에 대한 UIA 정보와 주변 이미지를 함께 확보합니다. 버튼 정보가 없으면 같은 선택을 이미지 대상으로 이어받습니다. 그 자리에서 이름과 선택 영역을 보여주며, 여러 후보가 남을 때만 영역을 좁히게 합니다.

수동 선택은 업무 버튼을 누르지 않는 오버레이 방식입니다. 선택 한 번으로 대상과 동작을 연결하고, 실행하지 않은 동작은 완료로 표시하지 않습니다.

동작 녹화

클릭·입력·선택·스크롤·단축키·드래그, 창 전환과 동작 전후 화면을 묶어 기록합니다. 영상만으로 작업을 추정하지 않습니다. 영상은 선택적인 복기 자료입니다.

녹화 중 실제 입력은 앱에 적용됩니다. 입력값을 읽지 못한 경우 기록되지 않은 값을 추측하지 않고 해당 단계에만 보완 표시를 남깁니다. 보호 입력을 감지하면 입력 기록과 관련 화면 캡처를 중단하거나 마스킹합니다. 비밀번호 영역을 식별할 수 없는 커스텀 화면은 민감 단계 전에 녹화를 일시정지하고 직접 처리하도록 합니다.

“값 입력 후 Enter”, “드롭다운을 열어 W 선택” 같은 의미 단위로 정리하되 원래 이벤트 순서는 보존합니다. 서로 다른 확정 동작 사이의 W→N 입력을 마지막 값 하나로 합치지 않습니다. 정지·일시정지는 즉시 반응하고, 녹화가 끝나면 초안을 바로 보여줍니다.

4. 저장한 작업을 대화로 바꾸는 방법

사용자 요청동작저장 작업 영향
“이번에는 조건을 N으로 실행해줘.”정의된 조건 입력값을 N으로 바꾸어 이번 실행에 전달기본값·단계는 그대로 유지
“앞으로 기본 조건을 N으로 바꿔줘.”해당 입력값의 기본값만 새 버전에 저장버전 증가, 이전 버전 복원 가능
“가족 조건 대신 장비 조건에 넣도록 바꿔줘.”이미 등록된 고유한 대상이면 단계 대상 참조만 변경. 대상이 불명확하면 편집창에서 그 단계만 선택다른 단계·이미지·완료 조건은 보존. 의미가 달라진 완료 조건은 함께 수정하도록 표시
“실행할 기기는 두 번째와 세 번째로 해줘.”현재 목록의 해당 두 기기를 먼저 구분하고 실행 대상을 고정이번 실행인지 기본 대상 변경인지 사용자 표현에 맞게 처리
“조회 후 결과가 나올 때까지 기다려줘.”고정 대기 대신 관찰 가능한 결과 조건을 추가해당 단계의 확인 조건만 갱신
“이걸 매번 쓸 수 있는 스킬로 만들어줘.”작업 ID·버전·입력값·시작 조건을 참조하는 설명과 호출 규칙 생성스킬에 좌표·비밀번호·거대한 이미지 사본을 넣지 않음

모델이 파일 전체를 읽고 다시 쓰게 하지 않습니다. 서버가 안정적인 단계 ID를 기준으로 필요한 필드만 수정합니다. 입력값에는 문자·숫자·날짜·선택 목록·기기 목록 같은 형식을 두고, 같은 값이 입력과 결과 확인에 쓰이면 같은 변수를 참조합니다.

명확한 수정 요청에는 변경 내용을 짧게 알려주고 적용합니다. 같은 이름의 입력칸이 여러 개이거나 적용 범위가 모호할 때만 질문합니다. 단순 값 변경 때문에 전체 재녹화를 요구하지 않습니다.

스킬은 저장한 작업을 찾고 올바른 입력값으로 호출하는 안내입니다. 실제 실행 책임은 MCP의 버전 고정된 작업에 둡니다. 스킬 호출 중 매 단계 LLM이 좌표를 다시 추론하지 않습니다. 스킬 파일 설치 위치와 형식은 사용하는 클라이언트에 맞는 내보내기 어댑터로 처리하고, 공통 실행 형식에는 종속시키지 않습니다.

창 연결실행 파일, 프로세스 생성 시각, 창 관계, 인스턴스 표시를 묶어 논리적인 창 ID 유지. 런처와 실제 앱의 프로세스를 구분MuMu 목록과 기기별 창을 분리하고, 다른 프로세스여도 승인된 앱 관계를 입증하면 연결
관찰대상과 관련 있는 UIA·화면·OCR을 선택. 본문 목표가 안 보이면 주변 버튼 개수와 무관하게 화면 경로 사용좌측 메뉴가 읽혀도 행 내부 실행 버튼이 없으면 해당 목록 영역을 시각 분석
대상 표현요소 이름, UIA 선택자, 이미지, 영역·기준점·행 관계를 하나의 Target으로 저장“▶ 아이콘” 대신 “선택한 기기의 행 안에 있는 ▶”
좌표·캡처물리 픽셀·논리 좌표·클라이언트 영역·축소 이미지 변환을 한 곳에서 관리. 현재 캡처의 좌표만 사용865와 1724의 차이를 측정하고 테두리·배율을 포함한 변환을 검증
입력화면 버튼은 실제 전경 입력을 기본으로 사용. UIA 의미 동작은 지원과 결과가 확인된 경우 사용. 앱별로 성공한 방법 재사용정확한 시작 버튼을 클릭하며, 익명 행 background 클릭으로 대체하지 않음
완료 확인값·선택 상태·연결된 새 창·의미 있는 이미지 변화·출력 파일 등 동작에 맞는 조건 사용“클릭 전달됨”이나 “창이 하나 늘었음”이 아니라 해당 기기의 실행 중 상태 확인

CUA Driver는 교체 가능한 어댑터로 둡니다. Driver 교체부터 시작하지 않습니다. 정확한 버튼의 전경 클릭·캡처·좌표를 독립 시험하고, 실패가 Driver에서 확인되면 Windows 기본 API 어댑터와 동일한 조건으로 비교합니다. 저장 작업과 편집창은 Driver가 바뀌어도 유지됩니다.

Windows Graphics Capture는 창·화면 프레임을 얻는 공식 경로이므로 GPU 기반 앱의 캡처 후보로 시험합니다. 대상 기기에서 지원 여부·빈 화면·가림·해상도 변경을 확인한 뒤 채택합니다. 보호된 화면이나 캡처 실패를 성공처럼 처리하지 않습니다. Microsoft 화면 캡처 문서

좌표는 공통 변환 서비스로 통일합니다. Windows UIA의 물리 좌표와 DPI 가상화된 창 좌표를 구분하고, 호출 주체와 대상 창의 DPI 조건을 기록합니다. API가 있다는 사실만으로 MuMu의 좌표 문제가 해결됐다고 판단하지 않습니다. UIA 화면 배율 문서 · DPI 좌표 변환 문서

이미지 매칭·OCR·화면 이해 모델의 역할 구분
  • UIA: 앱이 제공하는 입력칸·버튼·선택값 정보를 읽습니다.
  • 이미지 매칭: 전에 지정한 이미지가 지금 어디 있는지 찾습니다. 처음 보는 아이콘의 뜻은 이해하지 못합니다.
  • OCR: 화면에 그려진 글자와 위치를 읽습니다. 글자 없는 아이콘의 기능이나 조회 성공을 단독으로 판정하지 않습니다.
  • 화면 이해 모델: 처음 보는 화면에서 지시와 관련된 대상을 해석합니다. 여전히 선택 대상과 결과의 불확실성을 확인해야 합니다.

화면 이해는 연결된 사내 LLM 또는 명시적으로 구성한 사내 인식 서비스가 담당합니다. MCP는 임의의 외부 API 호출, 모델 다운로드, 원격 엔드포인트 변경을 추가하지 않습니다. 이미지나 화면 텍스트를 모델에 전달하면 그 모델·클라이언트의 데이터 처리 경로가 적용되므로 “MCP가 로컬이니 정보가 절대 PC 밖으로 나가지 않는다”고 설명하지 않습니다.

6. 한 번 성공한 작업은 더 짧은 경로로

반복 실행은 저장된 절차를 로컬에서 수행하고, LLM은 시작·변경·예외 처리를 담당합니다. 새 화면에서 목표를 이해하는 시간과, 이미 정해진 작업을 반복하는 시간을 분리합니다.

  • 같은 화면을 중복해서 읽지 않기: 한 번 관찰한 화면의 결과를 필요한 다음 단계에 재사용합니다. 입력·창 이동·화면 변화가 있으면 오래된 대상 참조는 무효화합니다.
  • 필요한 영역만 읽기: 전체 UIA 덤프나 전체 화면 이미지 검색 대신 저장한 목록·입력칸·결과 영역부터 찾습니다.
  • 완료되면 즉시 다음 단계: 무조건 5초 기다리기 대신 상태 변화 이벤트와 제한된 간격의 관찰을 사용합니다. 이벤트를 주지 않는 앱은 폴링을 사용합니다.
  • 프로세스 재시작 줄이기: 캡처·매칭 작업자를 지속 실행하고, 응답하지 않는 작업은 별도 작업자에서 시간 제한을 걸어 복구합니다.
  • 사람 확인은 필요한 지점만: 저장한 자동 완료 조건이 있으면 엔진이 확인합니다. 사용자가 명시한 확인 단계와 판정이 불명확한 단계만 사람에게 요청합니다.
  • 한 번 입력한 것은 함부로 반복하지 않기: 전송되지 않았다는 증거가 있으면 준비 후 다시 시도할 수 있습니다. 전송 여부를 모르면 현재 결과를 먼저 읽습니다.
속도를 높이기 위해 확인을 모두 없애지는 않습니다. 성공한 방법·대상 찾는 범위·완료 조건을 재사용하는 것이 핵심입니다. 앱 자체 부팅 시간과 LLM 응답 시간은 엔진 오버헤드와 따로 측정합니다.

초기 측정 목표: 캐시가 준비된 단순 로컬 단계의 엔진 시간 p95 ≤ 1초, 실패 감지·진행 상태 표시 ≤ 2초. 앱 로딩·사용자 대기·모델 응답 시간은 별도 공개합니다. 현재 달성한 성능 수치가 아니며 P0 실측 후 목표를 조정합니다.

7. 구현 순서와 완료 조건

P0 · 실제 MuMu의 최소 성공 경로부터 확인

현재 버전과 정확한 전경 입력 경로를 같은 환경에서 비교합니다. 창 발견 → 실제 시작 버튼 인식 → 클릭 → 해당 인스턴스 실행 확인을 각각 측정합니다. 좌표·캡처·권한·Driver·모델 인식 중 어디서 실패했는지 분리합니다.

완료 조건: 실제 시작 버튼 1개 성공과 첫 두 기기 구분. 시험 앱 통과로 대체하지 않습니다. 직접 제어가 계속 실패하면 UI 전면 수정에 들어가기 전에 어댑터를 결정합니다.

P1 · 공통 관찰·대상·입력·완료 엔진

UIA/이미지 세션을 사용자가 선택하는 구조를 없애고, 같은 요청 안에서 검증된 대상 참조로 조작하도록 통합합니다. 창 인스턴스, 좌표 변환, 중복 아이콘 범위, 상태 기반 대기를 구현합니다.

완료 조건: MuMu, 일반 Windows 폼, 웹 폼이 같은 계약으로 작동. 입력 없는 오류와 입력 후 불확실 결과를 구분하며 중복 클릭이 없어야 합니다.

P2 · 프로세스 편집창과 녹화 통합

사용자 선택은 편집창 하나로 통일합니다. 이벤트·화면·변경값을 단계로 변환하고, 누락된 단계만 수정하게 합니다. 자동 완료 조건 후보를 제안하고 사용자가 검토한 조건을 저장합니다.

완료 조건: MuMu에서 실제 녹화 → 검토 → 저장 → 앱 재시작 후 재생. 이미지 단계 때문에 무조건 매번 확인창이 뜨지 않아야 합니다.

P3 · 대화 수정·변수·스킬·빠른 반복 실행

단계 ID 기반 부분 변경, 입력값 형식, 실행 한 번의 값 덮어쓰기, 새 버전 저장·복원을 추가합니다. 검증된 절차를 스킬에서 호출하고 반복 실행 시 전체 탐색과 단계별 LLM 호출을 줄입니다.

완료 조건: 값과 대상 목록을 채팅으로 변경하고 원본·다른 단계·이미지를 보존. 이전 버전도 다시 실행할 수 있어야 합니다.

P4 · 기존 데이터 이동·실앱 검증·배포

기존 프로그램·작업·이미지를 백업 후 새 형식으로 복사 변환합니다. 원본은 보존하고 도구 노출은 새 연결부터 적용합니다. 패키지에서 실제 시험을 반복한 다음에 배포합니다.

완료 조건: 아래 수용 기준을 통과하고 실패 범위·실측 시간을 함께 공개. 출시 버전 번호는 이 게이트를 통과한 뒤 결정합니다.

이관할 때 기존 요소 보관함은 새 Target에 매핑하고 이미지 자산의 해시를 대조합니다. 사람이 확인하도록 저장한 단계는 임의로 자동 확인으로 바꾸지 않습니다. 진행 중인 v1 실행은 v1 실행기로만 이어가거나 명시적으로 정리하며, v2 작업으로 옮겨 자동 재개하지 않습니다. 이전 성공 프로필도 새 엔진에서 다시 확인한 뒤 사용합니다.

8. “제대로 된다”의 기준을 바꿉니다

기능별 단위 테스트 수만으로 완료를 판단하지 않습니다. 실제 사용 흐름과 실패 복구를 배포 패키지에서 확인합니다. 아래 항목은 앞으로 수행할 시험이며 아직 통과 결과가 아닙니다.

시험통과 조건
MuMu 말로 실행첫 두 행을 구분하고 실제 시작 버튼을 각각 한 번 클릭. 두 기기의 실행 중 상태와 창 연결을 개별 확인. 행 순서가 변해도 최초 지정한 대상 유지
MuMu 녹화·재생편집창 하나에서 실제 녹화·저장. 새로 열린 앱에서 재생하고 값·대상·결과가 일치. 수동 JSON 편집 없음
반복 아이콘·대상 변경다른 행의 같은 모양 아이콘을 누르지 않음. 첫째·둘째에서 둘째·셋째로 변경 시 해당 대상만 변경
다중 프로세스·팝업런처→플레이어→관련 팝업을 구분. 관계가 입증되지 않은 다른 앱으로 입력이 넘어가지 않음
배율·이동100·150·200%, 창 이동·크기 변경, 서로 다른 배율의 모니터에서 캡처와 입력 위치 일치. 미보유 환경은 미검증으로 명시
조회·입력·종료일반 폼에서 값 변경과 결과를 확인. 저장/종료 팝업 정책을 적용하고 실제 종료 확인. 지원하지 않는 조건은 부분 성공으로 분리
수정·버전이번 실행의 N 값이 기존 W 기본값을 바꾸지 않음. 영구 수정은 새 버전. 이미지·다른 단계 보존, 동시 수정 충돌 검출
불확실한 입력·중단응답 유실을 재현해도 같은 클릭 중복 없음. 중지 시 새 입력 즉시 차단. 완료된 단계는 재실행하지 않고 필요한 단계만 복구
속도·반복성기능별 원인 수정 후 초기 5회 연속, 배포 전 핵심 흐름 20회 반복. 성공률·오클릭 수·사람 개입 수·총시간·엔진/앱/모델 시간을 분리 보고
연결 모델·사내 경로이미지 지원/텍스트 전용 각각 확인. 지원되지 않는 화면 이해를 성공처럼 설명하지 않음. 구성되지 않은 외부 API 호출 없음

오클릭·중복 실행은 0건을 요구합니다. 20회 성공은 그 조건에서의 통과 증거이며 모든 프로그램의 일반 성공률을 의미하지 않습니다. 사내 앱·사내 LLM은 해당 환경에서 따로 검증하고 MuMu 결과로 대신하지 않습니다.

사용자 흐름 2개가 곧 MCP 도구 2개를 뜻하지는 않습니다. 읽기·수정·실행의 책임을 구분하면서 기본 노출 도구를 12개로 정리하는 안입니다. 아래 이름 중 새 이름과 인자는 제안이며 현재 도구 목록이 아닙니다.

모델이 화면에서 새 버튼 위치를 찾으면 관찰 ID와 해당 이미지 영역으로 요청하고 엔진이 현재 창·좌표·가림·신선도를 확인해 일회성 TargetRef를 만듭니다. 발급되지 않은 임의 참조나 오래된 전역 좌표는 받지 않습니다. 화면 내용은 업무 데이터로 취급하며 도구 권한을 확장하는 지시로 실행하지 않습니다.

UIA와 캡처는 완전히 원자적으로 얻는다고 가정하지 않습니다. 각각의 시각과 창 배치를 기록하고 차이가 있으면 다시 관찰합니다. 입력 직전에 창 이동·배율·전경·가림을 확인합니다. 포커스 변경·창 전환은 영구 좌표 재사용의 근거가 아닙니다. 짧은 단계 묶음도 각 입력 뒤 필요한 관찰을 새로 얻어 다음 대상을 확인하며, 첫 TargetRef를 모든 변경 단계에 그대로 재사용하지 않습니다.

사람 확인을 줄이기 위한 화면 판정·재개 계약

저장된 이미지의 출현·소멸, 특정 영역 OCR 값, 창 연결, UIA 값 같은 명시적인 조건은 로컬에서 확인합니다. 장면의 의미 해석이 필요한 경우에는 연결된 모델이 최신 화면을 보고 판단합니다. 두 결과는 같은 검증 등급으로 표시하지 않습니다.

실행기는 원래 run·단계·반복 회차·관찰·완료 조건·유효 시간을 모두 확인합니다. 화면이 바뀌거나 판정이 불확실하면 새 관찰을 요청하며 입력을 반복하지 않습니다. 모델의 “확신 99%”만으로 성공을 인정하지 않고 관찰 근거가 필요합니다. 시각 판단으로 확인된 결과는 visual_assessed로 남기며 정형 상태 검증으로 바꾸어 보고하지 않습니다. 사용자가 저장한 사람 확인 단계는 모델 판정으로 대체하지 않습니다.

LLM을 호출하는 주체는 현재 클라이언트입니다. MCP가 몰래 별도 모델을 호출하지 않습니다. 클라이언트가 이미지를 전달하지 못하는 경우 로컬 조건으로 확인 가능한 범위만 자동 실행하고, 그 외 해당 단계에만 편집창·사람 확인을 연결합니다.

실행 중인 작업은 처음 시작한 버전·입력값을 유지합니다. 그 사이의 편집은 다음 실행부터 적용합니다. 단순 문자열 전체 치환 대신 허용된 데이터 필드에만 변수를 넣습니다. 실행파일·권한·임의 코드·명령 문자열은 입력값으로 확장하지 않습니다.

목록 반복은 foreach로 범위를 제한합니다. 실행 시작 시 대상 목록을 고정하고, 최대 반복 횟수·전체 실행 시간·반복별 iteration_id와 완료 기록을 둡니다. 입력값이 달라지면 새 실행으로 시작합니다. 무제한 반복이나 임의 스크립트를 저장하지 않으며, 반복 중 목록이 바뀌면 고정한 대상의 현재 위치를 다시 찾습니다.

이미지·요소 지정은 편집창에서 만들고 변경합니다. 채팅은 기존 고유 대상의 재연결 또는 편집창의 특정 단계 열기를 요청합니다. 서버가 자산을 보관하므로 모델이 원본 이미지를 돌려보내지 않아도 수정할 수 있습니다.

MuMu 반복 행과 다른 프로세스의 창을 다루는 규칙
  • “첫 두 개”는 관찰 당시 첫 두 행의 인스턴스 정체성을 먼저 고정합니다. 첫 실행 뒤 목록이 재정렬되어도 새 첫 행을 두 번째 대상으로 삼지 않습니다.
  • 행 이름·현재 번호·주변 문구·행 구조 등을 묶어 구분합니다. 영구 식별자가 없다면 이번 실행의 임시 식별과 저장 작업의 재선택 규칙을 분리합니다. 구분 증거가 없는 행을 확실한 대상으로 저장하지 않습니다.
  • 이미지 템플릿을 창 전체에서 찾지 않고 목록 영역과 해당 행 안에서 찾습니다. 이미지 점수 하나만으로 대상 의미가 일치한다고 판단하지 않습니다.
  • 다른 프로세스의 새 창은 승인된 실행파일, 프로세스 생성 시각, 실행 연계, 창·인스턴스 정보로 연결합니다. 자식 프로세스이거나 같은 제목이라는 이유만으로 임의 앱까지 자동 허용하지 않습니다.
  • 실행 성공은 해당 행의 실행 중 상태와 연결된 인스턴스 창 등 작업별 증거로 판정합니다. 화면의 단순 변화, CPU 상승, 창 개수 증가만으로 성공하지 않습니다.
